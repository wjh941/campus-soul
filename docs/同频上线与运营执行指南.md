# 同频 Web 上线与运营执行指南

**版本：1.0｜适用阶段：小范围公开测试 → 稳定运营**

## 一、先说结论

当前代码、数据库迁移、生产部署和基础安全能力已经完成，适合进入“小范围邀请测试”。不建议在完成真实账号、真实设备和管理员流程验收前直接大规模开放或收费。

生产地址：

- https://campus-soul.vercel.app/
- https://wjh941.github.io/campus-soul/

## 二、已经完成的工作

- Supabase CLI 初始化、远端连接和迁移历史同步。
- 远端迁移状态已核对为最新，`supabase db push --dry-run` 显示数据库已是最新。
- Vercel 生产环境能够读取 Supabase 配置，生产入口返回 HTTP 200。
- 注册、登录、邮箱确认、密码找回入口。
- 用户资料、偏好、匹配、心动、消息、动态、评论、点赞。
- 附近发现、模糊位置、匿名聊天、双方同意揭晓。
- 举报、屏蔽、数据导出、账号注销、管理员审核基础能力。
- 动态图片 5 MB 限制，上传失败清理，评论 500 字限制。
- 登录异常、网络超时、缓存失效、Service Worker 更新和页面错误恢复。
- 移动端安全区、PWA、iOS/Android/鸿蒙 WebView 通用适配。
- 移除虚假活动数量、虚假未读和虚假社交证明。

## 三、你现在必须完成的控制台事项

### 1. Supabase Auth

进入 Supabase → Authentication → URL Configuration，确认：

- Site URL：`https://campus-soul.vercel.app`
- Redirect URLs：`https://campus-soul.vercel.app/**`
- 如使用 Pages：`https://wjh941.github.io/campus-soul/**`

用未注册邮箱测试注册验证和忘记密码。默认邮件服务适合测试和小规模邀请；公开运营前建议配置自定义 SMTP。

### 2. Storage

确认：

- `verification-evidence` 保持 Private。
- `profile-media` 是否公开由产品需求决定，策略必须限制本人写入/删除。
- `post-images` 可公开读取，但只能本人写入/删除。
- bucket 限制与前端一致：头像/生活照片 5 MB，动态图片 5 MB。
- 验证材料不得通过公开 URL 直接访问。

### 3. 管理员和数据库

- 创建独立管理员账号，不要使用日常测试账号。
- 开启管理员 MFA（如果 Supabase 方案允许）。
- 检查 RLS、Storage policies、RPC 权限。
- 开启数据库备份并确认恢复策略。
- 不要把 `service_role` 放进 Vercel 或前端代码。

## 四、上线前 90 分钟验收清单

### 双账号测试

准备 A、B 两个测试账号，分别在两个浏览器或两个设备完成：

- 注册、邮件确认、登录、退出、忘记密码。
- 填写昵称、学校、生日、资料和偏好。
- A 给 B 发送心动，B 回应心动。
- 双方进入消息，分别发送 3 条消息。
- 刷新页面、关闭再打开、切换网络，确认消息不丢失。
- 发布文字动态、上传图片、评论、点赞、删除自己的动态。
- A 举报 B，B 被 A 屏蔽，确认后续推荐不再出现。
- 导出数据，确认文件可以打开且内容范围合理。
- 用测试账号执行注销，确认不能继续使用已注销会话。

### 三类设备测试

至少覆盖：

- Android Chrome（你的 iQOO 可作为第一台）。
- iOS Safari 或 iPhone PWA。
- 鸿蒙浏览器或系统 WebView。

重点操作：

- 键盘打开时消息输入框和发送按钮可见。
- 相册授权、图片选择、上传失败重试。
- 定位允许、拒绝、重新允许。
- 横竖屏切换、返回键、PWA 冷启动。
- 弱网、断网、恢复网络。
- 长页面滚动到底部不被移动导航遮挡。

## 五、建议的小范围发布方式

第一批不要超过 20–50 位真实用户，邀请对象应集中在一个城市、学校或兴趣圈。原因是匹配产品首先要验证“局部密度”，不是追求注册总数。

建议发布节奏：

1. 第 1 天：邀请 5–10 人，观察注册和资料完成问题。
2. 第 2–3 天：扩展到 20–50 人，观察互相心动和回复率。
3. 第 4–7 天：修复高频问题，再决定是否扩大范围。

不要使用虚假的在线人数、等待人数、未读红点、倒计时或稀缺名额。

## 六、关键指标（每周记录一次）

只统计真实数据，首次测试先看趋势，不要追求虚高：

- 注册完成率：注册后完成邮箱确认的比例。
- 资料完成率：完成昵称、学校、生日、兴趣和简介的比例。
- 首次有效动作率：完成一次评测、偏好保存或查看推荐的比例。
- 首次双向心动率：发生互相心动的账号比例。
- 首次回复率：收到第一条消息后回复的比例。
- 次日回访率、7 日回访率。
- 消息发送失败率、图片上传失败率、页面错误数。
- 举报处理时长和误伤申诉数。

不要只看 PV、注册数或停留时间；对关系产品而言，真实回复和安全感更重要。

## 七、提高留存的真实做法

### 注册后的 3 分钟

让用户快速完成：

1. 生日和成年确认。
2. 昵称、学校、2–5 个关系品质。
3. 一次轻量评测或期待选择。
4. 查看有解释的推荐。
5. 使用一个可选聊天开场。

每一步都允许稍后继续，不要强迫用户填写过多隐私。

### 第二天回访

可以提供真实回访理由：

- 查看新的匹配解释。
- 继续完成未完成的资料。
- 查看自己的偏好趋势。
- 回答新的每日自我观察问题。
- 查看真实动态或继续一段尚未结束的聊天。

不要伪造“有人在等你”或“错过就没有”的压力。

### 关系质量

- 让推荐理由具体、可理解、可调整。
- 给出开场建议，但绝不自动发送。
- 明确举报、屏蔽和礼貌结束对话入口。
- 匿名聊天必须保持自愿退出和双方同意揭晓。
- 会员不能承诺获得匹配，付费功能应透明说明。

## 八、上线后第一周重点观察

每天检查：

- Supabase Auth 错误和邮件发送限制。
- Storage 使用量、异常大文件和公开验证材料风险。
- RLS 拒绝错误。
- Realtime 是否断连。
- 图片加载失败和弱网失败。
- 举报是否及时处理。
- 用户是否卡在邮箱验证、资料填写或首次匹配。

建议建立一个简单表格，记录：日期、问题、影响用户数、复现设备、处理结果、是否需要回归测试。

## 九、当前不应立即做的事情

- 不要直接全国开放。
- 不要在支付回调未完成验收前正式收费。
- 不要把验证材料设为 Public。
- 不要用 service_role key 做前端请求。
- 不要删除或重置生产数据库来解决迁移问题。
- 不要仅凭 Vercel HTTP 200 宣称所有业务无 Bug。
- 不要把非诊断性评测宣传成心理诊断。
- 不要承诺所有设备和所有网络环境绝对无故障。

## 十、后续开发优先级

### P0：正式测试前

- 完成双账号流程验收。
- 完成 Storage/RLS 实测。
- 完成 iOS、Android、鸿蒙设备实测。
- 确认 Auth 回调和邮箱验证。
- 确认管理员举报处理流程。

### P1：首批用户后

- 消息 Realtime 断线重连和发送后本地回显。
- 注册后自动进入可跳过的资料引导。
- 真实通知未读数量。
- 评测草稿恢复和保存失败重试。
- 会话摘要批量查询，避免大量匹配时 N+1 请求。
- 数据导出范围和账号注销后的 Storage 清理。

### P2：验证产品价值后

- 校园兴趣小组和小型活动。
- 更细的匹配反馈闭环。
- 自定义域名和品牌邮箱。
- 正式 SMTP、SPF、DKIM、DMARC。
- 经过真实数据验证的推荐质量优化。

## 十一、遇到问题时提供什么

向开发者反馈时提供：

- 手机型号、系统、浏览器版本。
- 页面地址和操作步骤。
- 页面提示文字或截图。
- 是否登录、是否 PWA、是否弱网。
- 大致发生时间。

绝不要提供：密码、验证码、Access Token、`service_role` key、完整 anon key、私密聊天内容和验证材料。

## 十二、最终判断

当前项目适合：

- 小范围真实用户测试。
- 单城市或单校园种子用户运营。
- 验证匹配质量和消息流程。
- 收集留存和安全反馈。

完成本指南中的 P0 验收后，再逐步扩大用户范围。产品真正的竞争力将来自真实用户密度、可解释匹配、低压力互动和持续的安全信任，而不是单纯增加页面数量。
